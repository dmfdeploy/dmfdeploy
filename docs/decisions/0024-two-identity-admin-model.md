**Rule:** Each app has a local admin that uses `vault_bootstrap_admin_username`, and the same human has an OIDC user mapped to `ops-admin`. Only Authentik, Zot and Grafana are sanctioned exceptions, and adding a fourth requires an amendment to this ADR.

## Context

The dmfdeploy platform's per-app admin identity has been spec'd informally since the 2026-05-08 Pre-Bao Bootstrap Secrets Design and observed in practice across six bootstrapped envs, but the model was never codified. On 2026-05-22 the `697-cms-awx-token.yml` playbook failed against the greenfield `<env>` env with HTTP 401 from AWX, because its admin-user fallback chain defaulted to the literal `awx-local-admin` while the rest of the role tree resolves the same value through `vault_bootstrap_admin_username | default('dmfadmin')`.

Survey results and fix commits: see the [archive record](../archive/decisions/0024-two-identity-admin-model.md).

## Decision

Adopt the **two-identity admin model** explicitly across the dmfdeploy platform:

1. **Local admin (per app).** A uniform `vault_bootstrap_admin_username` and `vault_bootstrap_admin_password` is materialised into each app at first install. The username comes from the init wizard's `OPERATOR_USERNAME` prompt; the password is a 32-char random generated by the wizard. The values flow into Ansible via the OpenBao bootstrap bundle. This identity exists for pre-Authentik bootstrap and as a break-glass after OIDC is live.

2. **OIDC user.** The same human enrols a passkey in Authentik under `authentik_bootstrap_passkey_username` (= `OPERATOR_USERNAME`) and is mapped to the `ops-admin` Authentik group. The blueprint at `dmf-infra/k3s-lab-bootstrap/roles/stack/operator/authentik/templates/blueprints/20-app-providers.yaml.j2` projects `ops-admin` as admin or superadmin in each OIDC-backed app (AWX SAML, NetBox, Forgejo, Grafana, Zot, dmf-cms). This is the day-to-day SSO identity.

3. **Sanctioned exceptions.** Three apps deliberately do NOT use `vault_bootstrap_admin_username` for their local admin:
   - **Authentik**: `akadmin` (Authentik bootstrap convention; humans never log in as this; they enrol a passkey under `authentik_bootstrap_passkey_username` instead).
   - **Zot**: `admin` (htpasswd format constraint; see the comment trail at `roles/stack/operator/zot/defaults/main.yml:25-38`).
   - **Grafana**: `admin` (Helm chart default; OIDC is the day-to-day path; an override could be added later but is not required).

   Adding a fourth exception requires an amendment to this ADR.

4. **Per-app local-admin email convention (amendment 2026-05-28).** The email stored at `secret/apps/<app>/admin.email` and materialised into each app's break-glass User row MUST follow the synthetic per-app, per-env pattern `<app>-<dmf_env_id>@<cert_manager_cluster_domain>`. Authentik keeps its bootstrap-convention email `akadmin@<base-domain>` (per the sanctioned exception above). `akadmin` is the Authentik admin identity. It is not the human's OIDC identity. The pattern is binding because app social_auth pipelines (NetBox, Forgejo, AWX) key on email for account linking. If the break-glass row carried the operator's email (`authentik_bootstrap_passkey_email`), the operator's first OIDC sign-in would silently merge INTO the break-glass row and compromise it (a C4 violation in spirit).
   - `dmf-env/bin/bootstrap-secrets.sh seed-bao` writes the canonical pattern for every non-Authentik app at first seed AND auto-heals legacy values (the operator email, empty string, or `admin@example.com`) on re-seed.
   - Role defaults (`netbox_superuser_email`, `awx_admin_email`, `forgejo_admin_email`) derive the same pattern when `vault_<app>_*_email` is unset. The previous fallback to `vault_bootstrap_admin_email` is removed; reintroducing it requires amending this ADR.
   - Live evidence and live-state remediation for already-deployed envs: see the [archive record](../archive/decisions/0024-two-identity-admin-model.md).

4. **Live-state read pattern (where applicable).** For apps whose local admin credentials are stored in a Kubernetes Secret (currently only AWX, via `<instance>-admin-password`), the `roles/common/admin-identity-resolve/` helper role reads the live Secret at runtime and falls back to caller-supplied values when the Secret is missing or incomplete. This eliminates the `wrapper-regenerated-password-doesn't-match-deployed-app` failure mode in 697 and `awx-integration`. Apps whose local admin credentials are stored in OpenBao (NetBox, Forgejo) read directly from OpenBao using the existing patterns; the helper does not apply.

## Consequences

- **Positive**: Codifies what was already implicit. New playbooks have a single answer for "what is the admin username/password fallback chain?" The wrapper-vs-cluster-password drift class for AWX is resolved without fresh rollout of envs.
- **Negative**: Adds one new role and a small amount of indirection. The helper's K8s-Secret scope means it does not help NetBox or Forgejo; those apps stay on their OpenBao-read patterns (no regression: they were never broken).
- **Neutral**: Greenfield envs see the same effective behaviour: the helper resolves the K8s Secret, which carries the wizard-set values, identical to the prior vault-only chain.
- Two backend-specific helper roles split on **where the credential lives**. They do not split on lifecycle, and each is the canonical implementation for its backend: `common/admin-identity-resolve` (K8s Secret, reads via `kubernetes.core.k8s_info`) and `common/app-admin-facts` (OpenBao at `secret/apps/<app>/admin`). The caller must include `common/openbao-session` (`mode: operator`) earlier in the same play. `app-admin-facts` has two modes: `materialize` (the default) reads or generates and writes; `live-read` is read-only and **source-atomic**: each candidate layer must supply BOTH `username` AND `password` or the layer is rejected. Resolution order: OpenBao → paired `app_admin_fallback_candidates` → scalar `app_admin_fallback_username`/`_password` → empty (`<prefix>_source: no-fallback`). `live-read` never writes, never generates and never emits `<prefix>_email`.
- Three code locations intentionally use neither helper. NetBox / netbox-sot roles read runtime and data secrets; those are not admin identity, so both helpers are out of scope. The `awx` install path syncs the password with `awx-manage update_password`, which is not identity resolution. `playbooks/verify-oidc-admin-bridge.yml` reads a single-token K8s Secret and has no username/password pair; both helpers expect paired credentials, and a `common/k8s-secret-key-resolve` helper for single-key lookups is deferred until a second use case appears.

### Enforcement

`dmf-infra/k3s-lab-bootstrap/tests/test-app-admin-facts-live-read.yml` is a fixture test, run by hand, that copies the `live-read` resolution Jinja from `common/app-admin-facts` and checks source-atomicity in six scenarios. No CI workflow runs it; dmf-infra CI only syntax-checks playbooks. discipline only: nothing mechanical checks the sanctioned-exceptions list, the email convention (`dmf-env/bin/bootstrap-secrets.sh` implements it but no test asserts it), or the K8s-Secret helper. All tasks touching passwords carry `no_log: true`; both helpers satisfy ADR-0007 (env-var-via-stdin pattern, no argv exposure).
